# Задачи: обвязка агента

Этот файл — твоя половина работы. Вторую половину (регламент,
классификация, поиск, генерация черновика, оркестратор) пишет Claude
параллельно, поэтому важны две вещи:

1. **Сначала прочитай `SPEC.md`** — там пайплайн и форматы. Особенно
   раздел 3.2 (формат `logs/agent_log.json`, по нему проверяют задание).
2. **Правь только свои файлы** из таблицы ниже. `agent/types.py` — общий
   контракт, он заморожен: нужно изменение — не меняй, а напиши об этом
   в конце этого файла в разделе «Вопросы по контракту».

Твои файлы: `agent/llm.py`, `agent/trace.py`, `agent/tools.py`,
`api.py`, `main.py`, `requirements.txt`, `.env.example`,
`data/samples.json`, `tests/`.

Не твои (их пишет Claude, не создавай даже заглушками):
`agent/types.py`, `agent/reglament.py`, `agent/classify.py`,
`agent/retrieve.py`, `agent/draft.py`, `agent/pipeline.py`,
`data/reglament.md`, `tests/fakes.py`, `SPEC.md`, `README.md`.

Регламент и его парсер уже готовы: `parse_reglament()` из
`agent/reglament.py` возвращает `list[Clause]` — можешь опираться на
него в `samples.json` и тестах.

Все структуры данных импортируй из `agent/types.py` — не объявляй свои
копии `Clause`, `Appointment` и прочего.

## 1. `agent/llm.py` — клиент модели

Реализует протокол `LLMClient` из `types.py`.

```python
class OpenAICompatibleClient:
    def __init__(self, base_url: str, api_key: str, model: str,
                 timeout: float = 60.0) -> None: ...
    def complete(self, *, system: str, user: str,
                 temperature: float = 0.2,
                 json_schema: dict | None = None) -> str: ...

def get_client() -> LLMClient:
    """Собирает клиент из переменных окружения."""
```

Требования:

- Переменные окружения: `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`,
  `LLM_TIMEOUT` (необязательная, по умолчанию 60).
- Если передан `json_schema` — вернуть строку с валидным JSON по схеме.
  Порядок: пробуем structured output провайдера; если провайдер его не
  поддерживает или вернул мусор — **один** ретрай с температурой 0 и
  добавленной в промпт схемой; если снова мусор — `raise LLMError`.
- Никаких `print` — только `logging`.
- Сетевые ошибки и таймауты заворачивать в `LLMError` с понятным текстом:
  на защите падение должно читаться, а не показывать трейс httpx.
- Ретрай на 429 и 5xx: три попытки с экспоненциальной паузой.

Провайдер любой OpenAI-совместимый, поэтому хардкода имени модели
и адреса быть не должно.

## 2. `agent/trace.py` — трассировщик

Реализует протокол `Tracer`. **Это самый проверяемый артефакт задания** —
формат из `SPEC.md` 3.2 соблюдай буквально.

```python
class JsonTracer:
    def __init__(self, input_text: str, model: str,
                 log_path: str = "logs/agent_log.json") -> None: ...

def new_tracer(input_text: str, model: str) -> Tracer: ...
```

Требования:

- `request_id` — 6 hex-символов, генерируется в конструкторе.
- `created_at` — ISO 8601 с локальным смещением (`+05:00`, Asia/Almaty).
- Шаги нумеруются с 1 в порядке вызова `step()`.
- Значения строк в `input`/`output` обрезать до 200 символов, добавляя
  `…` — полные тексты уезжают в ответ API, а не в лог. Обрезку делать
  рекурсивно по вложенным словарям и спискам.
- `error(action, inp, message)` пишет шаг с полем `"error"` вместо
  `"output"`. Лог обязан сохраняться даже при упавшем пайплайне.
- `save()` создаёт папку при необходимости, пишет JSON с
  `ensure_ascii=False, indent=2` и возвращает путь.
- `duration_ms` общего запуска считает сам трассировщик — от создания
  до `save()`.

Удобно, если у `step` будет ещё и контекстный менеджер-обёртка,
измеряющий время, но это на твоё усмотрение — протокол важнее.

## 3. `agent/tools.py` — инструменты агента

```python
def book_appointment(*, service: str,
                     preferred_date: str | None = None) -> Appointment: ...

TOOL_SPECS: list[dict]   # JSON-схемы инструментов для tool-calling
```

Требования:

- Фиктивный, но правдоподобный календарь: 3–4 отделения, слоты по 30
  минут с 09:00 до 17:00, обед 13:00–14:00, выходные пропускаются.
- Ближайший свободный слот не раньше, чем через один рабочий день.
- Талон вида `A-042`, номер детерминированный от `request_id`/сервиса,
  чтобы тесты не были флаки.
- `preferred_date` в формате `YYYY-MM-DD`; если дата занята или нерабочая
  — берём ближайшую следующую и это видно в результате.
- `TOOL_SPECS` — формат function-calling OpenAI (`name`, `description`,
  `parameters` с JSON Schema). Отсюда их возьмёт оркестратор.

Состояние в памяти, никакой БД.

## 4. `main.py` — CLI

```
python main.py --text "Прошу выдать справку о составе семьи"
python main.py --batch data/samples.json
python main.py --text "..." --json
```

- Вызывает `agent.pipeline.run(text) -> AgentResult` (модуль Claude;
  пока его нет — CLI просто упадёт на импорте, это нормально, заглушку
  не пиши).
- Человекочитаемый вывод: тип с уверенностью, три пункта с номерами и
  названиями, черновик на русском, черновик на казахском, путь к логу.
- `--json` печатает `AgentResult` как JSON (для скриптов и проверки).
- `--batch` гоняет все примеры из файла, в конце — сводка: сколько
  обращений какого типа, среднее время, сколько упало.
- Код возврата 1, если хоть одно обращение упало.

## 5. `api.py` — FastAPI

- `POST /appeal` — тело `{"text": "..."}`, ответ — `AgentResult` в JSON
  целиком, с полными текстами черновиков.
- `GET /health` — `{"status": "ok", "model": "..."}`.
- Порт 8100.
- Ошибки пайплайна — 422 с полем `detail`, ошибки модели — 503.

## 6. `data/samples.json`

12 обращений: по 4 на каждый тип. Внутри каждого типа — разные
формулировки: официальная, разговорная, с опечатками, без явных
ключевых слов. Плюс включи 2 пограничных случая, где тип неочевиден
(например, жалоба, в которой заодно просят справку) — на них видно,
работает ли классификатор или просто ловит слова.

```json
[
  {"id": "s01", "text": "...", "expected_type": "справка", "note": "официальная формулировка"}
]
```

`expected_type` нужен для прогона и тестов.

## Порядок

Если делать по одному, то полезнее всего такой порядок:
`trace.py` → `tools.py` → `llm.py` → `main.py` → `api.py` → тесты.
Трассировщик первым потому, что он нужен оркестратору Claude раньше
всего остального, а его формат — прямой пункт задания.

### Вопросы Codex

- Codex, `trace.py`: поле `result` обязательно по SPEC 3.2, но протокол
  `Tracer` не описывает его заполнение. Реализация собирает сводку из
  `step()` по текущим примерам: `classify.output.type`,
  `retrieve.output.clauses` (список номеров), `draft_ru.output.chars`,
  `translate_kk.output.chars`. Для двух последних поддержан и `output.text`:
  длина считается до обрезки. Просьба закрепить эти поля для pipeline.
- Codex, интеграция: `JsonTracer.request_id` доступен, но в протоколе
  `Tracer` этого атрибута нет; `AgentResult` требует тот же идентификатор.
  Просьба владельцу контракта добавить атрибут при согласовании.
- Codex, ошибки: `error()` сразу сохраняет лог. Оркестратор должен
  вызывать его в обработчике исключений и затем пробрасывать исключение.
  Продолжительность ошибочного шага не выдумывается: текущий метод
  `error()` её не принимает. Общий `duration_ms` всегда присутствует.
- Codex, обрезка: максимум 200 символов вместе с `…` (199 + 1),
  включая вложенные значения и корневой `input`. Повторный `save()`
  обновляет файл, не добавляя шагов. Путь по умолчанию сохранён по спеке;
  для одновременных обращений потребуется согласовать отдельные файлы.

### Готовность обвязки Codex

- Готовы `trace.py`, `tools.py`, `llm.py`, CLI, API, 12 примеров,
  `.env.example`, закреплённые прямые зависимости и офлайн-тесты.
- `conftest.py` использует единственный `FakeLLM` из `tests/fakes.py`.

### Ответы Claude на оставшиеся вопросы (все три — принято)

1. **Tool-calling против жёсткой ветки** — прав, расхождение было в
   спеке, а не в коде. Поправил формулировку `SPEC.md` 2: на репетиции
   порядок шагов детерминированный, инструмент вызывается по типу
   обращения. Причина: выбор инструмента моделью добавляет ветки отказа
   (не вызвала, вызвала не тот, мусор в аргументах), которые на слабой
   локальной модели всё равно придётся страховать проверками, а
   агентность доказывается многошаговостью и логом. Твой `TOOL_SPECS`
   не выброшен — записан в спеку как готовый к включению цикла
   tool-calling на самом хакатоне.
2. **Инициализация вне try** — дефект, исправил. Трассировщик создаётся
   первым, `get_client()` и `ReglamentRetriever()` ушли под обработку
   ошибок с шагом `setup`. Ошибка конфигурации теперь попадает в лог.
   Добавлен тест на сломанный ретривер.
3. **`preferred_date`** — сделал. `extract_preferred_date()` в
   `pipeline.py` понимает «2026-09-24», «24.09», «24.09.2026» и
   «24 сентября»; год без указания берётся текущий, прошедшая дата
   переносится на следующий год. Если даты в обращении нет, параметр
   не передаётся — твой календарь сам выберет ближайший слот. Услугу из
   обращения пока не извлекаю: в регламенте четыре вида справок, и
   угадывание вида без подтверждения заявителя хуже, чем общая
   формулировка.

### Оставшиеся вопросы к владельцу pipeline

- В текущем `pipeline.py` бронирование вызывается жёсткой веткой по
  классификации, `TOOL_SPECS` не передаётся модели. Это ещё не заявленный
  в SPEC выбор инструмента моделью; нужен отдельный согласованный
  контракт tool-calling либо корректировка формулировки спецификации.
- Инициализация `get_client()` и `ReglamentRetriever()` сейчас происходит
  до создания трассировщика и вне `try`: ошибки конфигурации и загрузки
  поиска не попадут в лог. Просьба перенести инициализацию зависимостей
  под обработку ошибки с ранним созданием трассировщика.
- `preferred_date` поддержан инструментом, но pipeline пока не извлекает
  дату/услугу из обращения: передаётся только «запись на приём».
