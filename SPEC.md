# Спецификация: AI-секретарь госоргана

Статус: v1, репетиция хакатона BAITC.
Документ — контракт. Код пишут параллельно два агента (Claude и Codex),
поэтому интерфейсы здесь важнее реализации.

---

## 1. Задача

На вход — текст обращения гражданина. На выходе:

1. тип обращения: `справка` / `жалоба` / `запись`;
2. три релевантных пункта вымышленного регламента с номерами;
3. черновик ответа на русском и казахском со ссылками на эти пункты;
4. JSON-трассировка всех шагов агента в `logs/agent_log.json`.

Предметная область регламента: услуги ЦОН-типа — выдача справок,
социальные выплаты, запись на приём, порядок рассмотрения жалоб.
Регламент вымышленный, но связный и пронумерованный.

## 2. Принцип работы

Агент построен на tool-calling: модель сама решает, какой инструмент
вызвать, оркестратор фиксирует каждый шаг. Ветка `запись`
дополнительно вызывает инструмент бронирования.

```
обращение
   │
   ▼
[classify]  ──► Classification (тип + уверенность + обоснование)
   │
   ▼
[retrieve]  ──► list[Clause] ровно из 3 элементов
   │
   ├─ если type == "запись" ──► [book_appointment] ──► Appointment
   │
   ▼
[draft_ru]  ──► текст на русском, обязательно со ссылками на пункты
   │
   ▼
[translate_kk] ──► тот же текст на казахском
   │
   ▼
AgentResult + logs/agent_log.json
```

Почему не LangGraph: на четырёх шагах граф добавляет слой абстракции,
но не добавляет ясности, а на защите важен читаемый лог. Оркестратор —
обычная функция в `agent/pipeline.py`.

## 3. Контракты

Все структуры данных объявлены в `agent/types.py` — это единственный
источник истины. Файл уже написан; менять его в одностороннем порядке
нельзя (см. раздел 6).

### 3.1 LLM-клиент

```python
class LLMClient(Protocol):
    def complete(
        self,
        *,
        system: str,
        user: str,
        temperature: float = 0.2,
        json_schema: dict | None = None,
    ) -> str: ...
```

Провайдер — любой OpenAI-совместимый API, адрес и модель берутся из
`.env`. Если передан `json_schema`, клиент обязан вернуть строку с
валидным JSON по этой схеме (structured output либо ретрай с починкой).

### 3.2 Трассировка

```python
class Tracer(Protocol):
    def step(self, action: str, *, inp: dict, out: dict,
             duration_ms: int, meta: dict | None = None) -> None: ...
    def tool_call(self, name: str, *, args: dict, result: dict,
                  duration_ms: int) -> None: ...
    def save(self) -> str: ...   # возвращает путь к записанному файлу
```

Формат `logs/agent_log.json` — фиксированный, по нему проверяют задание:

```json
{
  "request_id": "b3f1a2",
  "created_at": "2026-09-21T13:40:11+05:00",
  "input": "Прошу выдать справку о составе семьи",
  "model": "qwen3-35b",
  "steps": [
    {
      "step": 1,
      "action": "classify",
      "input": {"text": "Прошу выдать справку..."},
      "output": {"type": "справка", "confidence": 0.94},
      "duration_ms": 820
    },
    {
      "step": 2,
      "action": "retrieve",
      "output": {"clauses": ["3.1", "3.4", "7.2"], "scores": [0.81, 0.77, 0.64]},
      "duration_ms": 140
    }
  ],
  "tool_calls": [
    {"name": "book_appointment", "args": {"service": "справка"},
     "result": {"ticket": "A-042"}, "duration_ms": 12}
  ],
  "result": {"type": "справка", "clauses": ["3.1", "3.4", "7.2"],
             "draft_ru_chars": 812, "draft_kk_chars": 794},
  "duration_ms": 4310
}
```

Поле `result` собирается трассировщиком из уже записанных шагов:
`type` из `classify.output.type`, `clauses` из `retrieve.output.clauses`,
`draft_ru_chars` и `draft_kk_chars` — из шагов `draft_ru` и
`translate_kk`. Оркестратор передаёт в эти шаги `output.text` с полным
текстом, длина считается до обрезки. Названия шагов `classify`,
`retrieve`, `draft_ru`, `translate_kk` закреплены — трассировщик
опирается на них.

`request_id` генерирует трассировщик и отдаёт через атрибут
`Tracer.request_id`; оркестратор берёт его оттуда в `AgentResult`,
второй раз не генерирует.

Обработка ошибок: `error()` записывает шаг и сразу сохраняет файл, после
чего оркестратор пробрасывает исключение дальше. Длительность упавшего
шага не пишется — выдумывать её незачем, общий `duration_ms` есть всегда.

Обрезка: 200 символов итогового значения вместе с многоточием,
рекурсивно по вложенным структурам и по корневому `input`.

Известное ограничение: все запуски пишут в один
`logs/agent_log.json` — так требует задание («лог рядом с кодом»).
Для параллельных обращений через API этого мало, но на репетиции
параллелизм не демонстрируется; если понадобится, добавим
`log_path` на вызов отдельным изменением спеки.

Правила: шаги нумеруются с 1 по порядку выполнения; длинные тексты в
`input`/`output` обрезаются до 200 символов (полные тексты — в ответе
API, не в логе); лог пишется даже при упавшем шаге, с полем
`"error"` вместо `"output"`.

### 3.3 Регламент

`data/reglament.md` — размеченный markdown. Заголовок пункта строго:

```
## 3.4 Сроки выдачи справки о составе семьи
```

То есть `## <номер> <название>`, номер вида `N.N`. Парсер опирается
именно на этот формат, свободную нумерацию ломать нельзя.

### 3.4 Поиск

Эмбеддинги `BAAI/bge-m3` через `sentence-transformers`, косинусная
близость, индекс строится в памяти при старте (регламент — 2–3 страницы,
векторная БД тут избыточна). Возвращается ровно 3 пункта, отсортированных
по убыванию score. Если максимальный score ниже `RETRIEVE_MIN_SCORE`
(по умолчанию 0.35), пункты всё равно возвращаются, но в черновик
добавляется оговорка о необходимости уточнения — галлюцинировать
номера пунктов запрещено.

### 3.5 Черновик ответа

Русский текст генерируется первым, казахский — переводом русского
(не независимой генерацией), чтобы номера пунктов и факты совпадали.
В обоих языках обязательны: обращение к заявителю, ссылка минимум на
один пункт регламента в виде `п. 3.4`, срок рассмотрения, подпись
органа. Для типа `запись` — дополнительно дата, время и номер талона
из `Appointment`.

## 5. Разделение работы

Правило простое: **каждый правит только свои файлы.** Пересечений нет,
поэтому мержить нечего.

| Файл | Владелец |
|------|----------|
| `agent/types.py` | Claude (заморожен) |
| `agent/reglament.py` | Claude |
| `data/reglament.md` | Claude |
| `agent/retrieve.py` | Claude |
| `agent/classify.py` | Claude |
| `agent/draft.py` | Claude |
| `agent/pipeline.py` | Claude |
| `SPEC.md`, `README.md` | Claude |
| `agent/llm.py` | Codex |
| `agent/trace.py` | Codex |
| `agent/tools.py` | Codex |
| `api.py` | Codex |
| `main.py` | Codex |
| `requirements.txt`, `.env.example` | Codex |
| `data/samples.json` | Codex |
| `tests/conftest.py` | Codex |
| `tests/fakes.py` | Claude |
| `tests/test_<модуль>.py` | владелец `<модуль>` |

Claude делает «мозги» агента — логику решений и предметное содержание.
Codex делает обвязку — клиент модели, инструменты, трассировщик, CLI,
API, тесты. Обе половины собираются друг с другом только через
`agent/types.py`, поэтому порядок готовности не важен.

Тесты: каждый пишет тесты на свои модули в отдельный файл
`tests/test_<модуль>.py` — так владение по файлам сохраняется и
внутри `tests/`. Общие подделки (`FakeLLM` и прочее) живут в
`tests/fakes.py`, его пишет Claude, потому что он нужен ему раньше;
`conftest.py` их только импортирует и превращает в фикстуры.

Заглушки: пока чужой модуль не готов, вызывайте его по контракту из
`types.py` и не заменяйте своей реализацией — иначе получим два
несовместимых клиента модели.

## 6. Изменение контракта

`agent/types.py` и форматы из раздела 3 менять в одиночку нельзя.
Нужно изменение — сначала правка в `SPEC.md` отдельным коммитом с
пометкой `spec:` в заголовке, затем правка `types.py` владельцем файла.
Так второй агент видит причину, а не только последствия.

## 7. Готовность

Задание считается сделанным, когда:

- [ ] `python main.py --text "..."` печатает тип, три пункта и оба черновика;
- [ ] `logs/agent_log.json` соответствует формату из 3.2;
- [ ] `data/reglament.md` содержит не меньше 12 пунктов в формате 3.3;
- [ ] `python main.py --batch data/samples.json` проходит по всем примерам без падений;
- [ ] ветка `запись` даёт непустой `Appointment` с номером талона;
- [ ] `pytest` зелёный.

Демо на защите: одно обращение каждого типа плюс показ `agent_log.json`
как доказательства многошаговости.
